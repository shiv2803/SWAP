# SWAP Link Predictor — Arduino UNO Q App

Deploys `laptop_training/swap_random_forest.joblib` (the RandomForestClassifier
trained by `laptop_training/train_model.py`, explicitly built for "the UNO Q
inference engine") onto the UNO Q's Linux (MPU) side, and drives protocol
selection via the MCU (sketch) side.

The UNO Q has two processors, so this is a two-part app:

- `python/main.py` — runs on the Linux side. Registers a Bridge handler for
  `telemetry_line` notifications, runs `model.predict()` on each parsed JSON
  frame, and calls `force_protocol` back on the sketch with the result.
- `sketch/` — runs on the real-time MCU. `sketch.ino` is a copy of
  `../uno_q_mcu_sketch/sketch.ino` (a Node A UART forwarder: relays
  newline-delimited JSON telemetry from Node A up to Python via
  `Bridge.notify("telemetry_line", ...)`, and exposes
  `Bridge.provide("force_protocol", ...)` for Python to call back down). The
  original stays at `../uno_q_mcu_sketch/` as the source of truth — if you
  edit the sketch, edit both, or drop this copy for a symlink.

## Upload via Arduino IDE (App Lab) — GUI

1. Connect the UNO Q to this PC over USB and power it on.
2. Open the **Arduino IDE**. It should detect the UNO Q's App Lab
   environment (App Lab appears as a panel/tab once the board is selected —
   if it doesn't show up, install/update the **UNO Q board core** first via
   **Tools > Board > Boards Manager**, search "UNO Q").
3. In App Lab, choose **Open existing app** (or **File > Open**) and point it
   at this folder: `uno_q_app/`.
4. Select the UNO Q board and its port under **Tools > Board / Port**.
5. Click **Run/Upload** (▶). App Lab will:
   - install `python/requirements.txt` on the Linux side,
   - compile and flash `sketch/sketch.ino` to the MCU,
   - start `python/main.py`.
6. Watch the **Monitor**/serial log pane — you should see:
   ```
   Loaded model from .../swap_random_forest.joblib (features: [...])
   Bridge ready
   node=a predicted=WIFI confidence=0.9x raw=[-65.0, 0.02, -70.0, -95.0, 6.0, 0.04, 12]
   ```

If your IDE version doesn't show an App Lab panel, use the CLI path below
instead — same files, no GUI needed.

## Upload via CLI (fallback, if App Lab GUI isn't available)

The UNO Q's Linux side exposes itself over USB as a network device with SSH.
From a terminal:

```bash
# find the board's IP (check Arduino IDE's board info, or your router / `arp -a`)
scp -r uno_q_app arduino@<UNO_Q_IP_ADDRESS>:~/ArduinoApps/uno_q_app
ssh arduino@<UNO_Q_IP_ADDRESS>
arduino-app-cli app start ~/ArduinoApps/uno_q_app
arduino-app-cli app logs ~/ArduinoApps/uno_q_app
```

Stop it with `arduino-app-cli app stop ~/ArduinoApps/uno_q_app`.

## Before you go further

- **Wire up real Node A hardware.** The sketch expects Node A's UART on
  `Serial1` (D0/D1, 115200 8N1) — see `../uno_q_mcu_sketch/README.md` for
  wiring/baud details before uploading.
- **Schema mismatch — fixed 2026-08-23.** The model used to be trained on a
  fictional `wifi_rssi,ble_rssi,lora_rssi,lora_snr,pdr,rtt,retries` schema
  with no real `pdr`/`retries` source; `laptop_training/train_model.py` now
  trains on `wifi_rssi,wifi_loss,ble_rssi,lora_rssi,lora_snr,lora_loss,rtt_ms`
  — the real fields the sketch's `telemetry_line` frames carry — using
  `telemetry_log.csv` (real recorded telemetry) and labels generated by
  `swap_backend.link_quality_model.compute_raw_scores` (the same heuristic
  formulas the backend's rule-based path uses, so labels can't silently
  drift from it). `python/main.py` reads the feature list straight from
  `feature_sequence.txt` and pulls each field directly off the parsed JSON
  — no stubbing. If you retrain, `laptop_training/train_model.py` is the one
  script to run; it writes both the model and `feature_sequence.txt`, and
  `main.py` picks up whatever order that file says.
- This model (100 trees, `max_depth=8`) is a *different* model from
  `models/link_quality_rf.joblib` used by the FastAPI backend
  (`swap_backend/`) — that one predicts on rolling **10-record window
  means** with a hysteresis/dwell governor on top, while this one predicts
  per single telemetry line (no windowing) since the UNO Q app runs
  Bridge-notification-driven, not on a buffered loop. Same feature set and
  same label formulas now, different inference granularity.
